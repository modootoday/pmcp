Docs / Command reference

Command reference

Back to the overview

Every pmcp command with its flags, behaviour and exit codes. pmcp <command> --help prints the same usage from the command itself, with its subcommands and examples, and pmcp <command> <subcommand> --help prints the usage, options and examples of one subcommand, such as pmcp harness group create --help or pmcp mailbox export --help.

The invocation a host uses

  • pmcp opens a workspace on a supported terminal; a piped launch runs the MCP server on stdio.
  • pmcp --root ./node_modules: a leading option with no command is still a server, because hosts pass options without one.

An unrecognised command does not fall through to a server the caller did not ask for. Only an empty argument list, or one that begins with an option serve accepts, takes that path. -v, -V, --version and version print the version; any other leading option, such as -x or a misspelled --verison, is an unknown option and exits 2 without reading standard input.

status

pmcp status [--config <file>] [--json]

Show enabled features and their TOML or auto source, projection drift, live sessions, pause, leases, unseen broadcasts, worktree ahead/behind counts, shared MCP credential presence, logged errors from the last hour, and, with a [budget] table, each limit beside what it measured, and how many are over. Reads do not acknowledge broadcasts, refresh credentials, prune logs, fetch or move git refs. Projection uses the same check as project --check. Exit 0, or 4 when projection drift exists; 2 when there is no pmcp.toml. A limit over its number is reported and never changes the exit code: project --check is the one that judges it. Linked worktrees ahead of or behind the mainline are live state in a multi-session workspace: the summary and data.lagging count them, and they never change the exit code. Missing or invalid input follows the normal usage/failure exit contract. Human output is a compact summary on stdout; JSON retains the full details.

init

pmcp init [--preset solo|multi-session] [--force]

Create pmcp.toml in the current directory. Solo enables Claude/Codex targets, the stage-all and heredoc guards, and detected git settings. Multi-session adds registry, pause and broadcast; in git it also enables worktree commands and shared-checkout warnings. Git remote and mainline come from the same detection used by the git workflow. No gate, installation command, MCP credential or provider is invented. Both presets are parsed and compiled before writing. Existing files require --force. Output explains each choice; projection remains a separate explicit operation. Exit 0 on creation, 2 for a bad preset or refused overwrite, 1 for a write failure.

hooks

pmcp hooks list [--runtime claude|codex] [--config <file>] [--json]
pmcp hooks test --runtime claude|codex --event before_tool --command "git add -A" [--json]
pmcp hooks test --runtime claude --event before_tool --path fixture.txt --session-state state.json

List compiled policies per runtime and neutral event, including mode and source table. Test constructs a synthetic payload in that runtime's recorded shape, normalizes it, runs policy selection and composition, lowers unsupported asks, and renders the native response. The event accepts a neutral name or a supported native name. Choose at most one of --command, --path and --tool; these selectors require a tool event. Tool accepts a native name or shell, edit, read or other, subject to that runtime's tool vocabulary. No native runtime or model call is needed.

Session state is isolated in a temporary directory, then removed. Commands and patches are classified, never executed. External custom guards, validators, Stop projection subprocesses and worktree synchronization are explicitly marked skipped. Their simulated context reports this limitation; the command does not claim a full live result. Exit 0 means the simulation completed, even when the rendered decision denies; invalid input exits 2. Per-policy timings and reasons precede the rendered output in human mode. Each policy row also gives raw, {verdict, reason} as the guard found it before its mode, so a guard in observe, warn or graded mode shows what deny would have done; human mode adds it as (observe; found deny: …) where it differs.

--session-state accepts a JSON object with optional records (session records with valid 8–64 character IDs), pause (by, reason, since), leases (name to pid, subject, since, optional cwd), and broadcast (id, by, text, since). Pause and broadcast may be null. Existing liveness and unseen-broadcast rules apply. This file and the real session store remain unchanged.

pmcp hooks report [--since 2d] [--json]
pmcp hooks report --switch-check shell.heredoc [--since 2d] [--json]

report summarises the guard lines the hook bundle writes to the project log at debug level ([logging] level = "debug", or PMCP_LOG=debug). For each guard and runtime it counts the runs, what the guard found before its mode (raw: allow, deny, ask) and what the call got, the modes seen, the sessions, and the p50, p95 and longest durations. Sessions matching a [hooks.report] exclude_sessions regex (replays, smoke runs) are left out and counted. --since takes a duration such as 10m, 2h or 3d, or an ISO time. --switch-check <guard> lists instead the calls that guard found something in and let through, because it was in observe or warn: what deny would have refused. The log holds no command, prompt or transcript text, so neither does the report. --json prints {version, since?, lines, sessions, excluded, guards}, or {version, guard, refused} with --switch-check.

JSON output

Every command that prints a result takes --json and then writes exactly one line to standard output, a JSON envelope, whether it succeeded or failed:

{
  "schema": "pmcp.hooks.list.v1",
  "ok": true,
  "data": { "version": 1, "policies": [] },
  "errors": []
}
  • schema is pmcp.<command>[.<subcommand>].v1, such as pmcp.status.v1, pmcp.git.worktree.list.v1 or pmcp.models.v1. A change that removes or retypes a field gets a new version.
  • ok is true exactly when the exit code is 0 (see Exit codes); status with drift prints its report with ok: false and exit 4.
  • data is the command's result: the object the tables below describe, the array models lists, or null when the command failed before it had one.
  • errors lists {code, message} for each error the command reported; code names the exit code (failure, usage, missing_optional, differences, busy). A usage error such as an unknown option still prints an envelope, with data: null.

No colour or human text is mixed into standard output; the same errors also go to standard error. Without --json every command prints human output (mcp status and the tui receipts included). mailbox and harness are machine protocols: they always print their own JSON receipts ({ok, data} and {schemaVersion, ok, ...}), take no --json, and are unchanged. logs without --json keeps its JSONL stream.

The data of these commands has a published schema in schemas.json, with version: 1 inside data; each entry under schemas uses the shared root $defs, and envelope describes the wrapper. Consumers must allow unknown fields inside session, decision and log records. Tokens are never part of an auth status object.

Worktree counts are omitted when the upstream cannot be compared; absence does not assert equality. Status auth rows add a redacted error when credentials are unavailable or invalid. It only reads: no record is pruned and nothing is written. Mutating sessions, git and MCP verbs reject --json.

serve

pmcp serve [--config <file>] [--root <dir>] [--scope <prefix>] [embedding options]

Reachable by name so it appears in help. It writes nothing to standard output: from the moment it starts, standard output is the protocol, and a diagnostic printed there corrupts the stream.

list

pmcp list [--root <dir>] [--scope <prefix>] [--json]

The skills discovered in node_modules, as two aligned columns, or as JSON for a script. This is the command that answers "would the server see anything from here".

marketplace

pmcp marketplace list --json
pmcp marketplace export typescript-5 --runtime agy --output ./typescript-plugin
agy plugin install ./typescript-plugin

List the bundled free plugins or export one selected native package. Choose claude, codex, gemini, grok or agy. An export preserves existing destinations and does not edit runtime configuration or bypass native installation consent. CLI discovery includes the built-in catalog unless --no-builtin or [catalog] builtin = false is configured.

An empty catalog is a finding rather than a success. It exits 1 and names the roots it walked, because a project that installed this and sees nothing has a misconfiguration worth an exit code.

index

pmcp index [--config <file>] [embedding options] [--local-only] [--dry-run] [--force] [--json]

Encodes each description once so ranking can be semantic, and stores the vectors beside the tree they describe, so two projects never share one index. Only what changed is re-encoded; an unchanged description produces the same vector at the same cost as the first time.

Vectors written by one model are never scored against another, so --model is part of the key rather than a preference. Without the optional peer installed it exits 3 and tells you ranking stays lexical, which is the default and not a failure.

A partial index is reported rather than called success: it exits 1 and says how many of the catalog it covered, because ranking needs a vector for every entry and falls back to lexical without one.

models

pmcp models [--json]

Lists the default E5 encoder and optional EmbeddingGemma presets with their dimensions and asset revisions. It does not load an encoder or download weights. Configure [embedding] in pmcp.toml or override individual settings on the CLI.

pmcp index --model embeddinggemma-2 --dtype q4 --dimensions 256
pmcp serve --model embeddinggemma-2 --dtype q4 --dimensions 256

Shared embedding options are --model, --dtype, --dimensions, --model-revision, --model-path, --model-cache, --query-prefix, --passage-prefix, and --pooling. They override the corresponding configuration fields. Use --no-config for an independent CLI selection. Model identity includes revision, dtype, dimensions, prefixes, pooling, and projection, so incompatible vectors and query caches stay separate.

index --local-only refuses downloads, --dry-run previews work without loading a model or writing vectors, and --force rebuilds only the selected encoder's index. serve never downloads weights: it uses a complete matching local index or reports a lexical fallback. Restart after switching encoder settings.

mailbox

pmcp mailbox init --config ./pmcp.toml
pmcp mailbox actor --config ./pmcp.toml --actor reviewer --actor-file /private/reviewer.actor.json
pmcp serve --config ./pmcp.toml --mailbox-actor-file /private/reviewer.actor.json --mailbox-runtime codex-cli

Mailbox is disabled by default. Initialization creates a project UUID and preserves existing configuration. A launcher-bound actor enables mailbox_send, mailbox_inbox, mailbox_read, mailbox_ack, and mailbox_sessions. Reading records a receipt; acknowledgement requires reading first. Acknowledgement does not assert task completion.

Credentials and attachment files contain secrets and must stay outside source control. State defaults to the user's XDG state directory. Administrative rotate, export, backup, and restore operations require --operator. Use pmcp mailbox --help for inputs. The mailbox exchanges peer data; the host owns authentication, automatic runtime delivery, and enterprise policy.

project

pmcp project
pmcp project --check [--smoke]
pmcp project import-mcp --source codex:/path/to/config.toml
pmcp project exec-mcp remote

exec-mcp <alias> is what a projected native entry runs to start a declared MCP server with its resolved environment, or, for auth = "pmcp", the shared-auth proxy; you rarely run it by hand. See shared remote MCP authentication.

Generate selected runtimes' native files from pmcp.toml. Unmanaged entries and credential references are preserved; conflicts stop the write. --check reports drift without writes (exit 4), and MCP import previews changes by default; --write applies them. --check --smoke then runs the [hooks.test] fixtures file as pmcp hooks test --fixtures does, and exits 4 on any finding. Configuration and guard examples.

Configuration files and the ownership lock are replaced atomically one file at a time. If projection is interrupted, inspect with pmcp project --check, then run pmcp project explicitly to repair drift. Projection does not start a runtime or replay terminal input. The complete set of files is not a single transaction.

sessions

pmcp sessions status
pmcp sessions pause "release freeze" [--by <name>]
pmcp sessions resume
pmcp sessions broadcast "main moved; rebase before delivering" [--by <name>]
pmcp sessions unbroadcast
pmcp sessions sweep
pmcp sessions send --to <selector>... [--subject <s>] [--wake] <body>
pmcp sessions inbox

Coordinate the live agent sessions of this repository and its worktrees, through the state the hooks keep for [sessions]. status (the default verb) prints each live session, the pause, current broadcasts, held leases and undelivered edits in a shared checkout to standard output, or no live sessions. pause refuses edits and mutating commands in every other session until resume; broadcast delivers its text once to each session as context, and unbroadcast withdraws it. --by names the sender, whose own session is exempt; without it the sender is the agent session the command runs in, or operator from the operator's terminal (--by operator is refused anywhere else). pause and resume are operator verbs: inside an agent session they exit 1 with a line naming who to ask (see the operator). sweep removes records whose process is gone. send addresses all, session:<id>, alias:<name>, role:<name> or worktree:<path> through [sessions.mailbox]; inbox lists your messages. Run several agents walks through them. Exit 0, or 2 for an unknown verb, missing text or no pmcp.toml.

logs

pmcp logs --since 10m --level warn --pretty
pmcp logs --session 4f92 --component hooks
pmcp logs --trace 7cef825e8fbd8c3f
pmcp logs --follow

Read this project's JSONL logs from the state directory, or the file [hooks] error_log names. Filters combine: --session takes an id prefix, --trace one hook call, --component a component and those below it, --level that level and more severe, --since a duration (10m, 2h, 3d) or an ISO time. Records print as JSON lines unless --pretty; --follow keeps printing until interrupted. Secret values, prompt text and environment values are redacted at write time, per [logging]. Exit 0, or 2 for an unusable filter or no pmcp.toml.

git

pmcp git worktree create review [--base <ref>]
pmcp git worktree list
pmcp git worktree sync
pmcp git deliver [<commit>...] [--during-pause] [--no-push] [--json]
pmcp git sync
pmcp git affected --base <ref> [--head <ref>] [--tests-only] [--json]

The git workflow configured by [git]. Each subcommand needs its table; without it, or without a pmcp.toml, the command exits 2 and names what is missing.

  • worktree create <alias> makes a linked worktree under [git.worktrees] root on a new branch from the upstream (or --base), links the configured files from the main checkout, runs bootstrap, and prints the path.
  • worktree list prints alias, branch, behind/ahead and path for the main checkout and each linked worktree.
  • worktree sync moves the current worktree onto the mainline when that loses nothing; exit 1 when it is held back.
  • deliver fetches, replays the named commits (default: the ones the upstream lacks) onto the mainline, runs the gate in its own tree under a lock, and pushes; it replays again if the mainline moved. A delivery that touches a leased path holds that lease until it has pushed and installed, and it refuses during a pause unless --during-pause (an operator verb, refused inside an agent session) or during_pause = "allow". --no-push replays and runs the gate command, then stops: it takes no lease and pushes, syncs and notifies nothing, and it refuses gate = "pre-push", where the push is the gate. Deliver never takes the host lease: replay, gate tree, hooks and push run without it, and the gate wraps only its test stages in pmcp heavy --profile gate. Exit 0 delivered, gated with --no-push, or nothing to deliver; 1 refused, fetch failed, gate failed or attempts exhausted; 2 --no-push with the pre-push gate; 75 the gate command exited 75 because a test stage never got the host lease ("gate not run: host busy"), so nothing was pushed.
  • sync moves the main checkout to the mainline, installs when a listed file changed, and follows clean submodule pins. Exit 0 moved or already equal, 1 when local work would be lost or the fetch failed, 2 when blocked (undelivered edits, another branch, a git operation in progress). Run in a desk (a linked worktree matching [git.worktrees] desks), it brings the desk up to date the same way without rebasing: exit 0 moved or current, 1 held (an unlanded commit, uncommitted tracked edits, a pause, another session's lease, a git operation in progress), with the reason. In any other linked worktree it exits 2.
  • affected --base <ref> prints the workspace members the delta from <ref> to --head (default HEAD) touches, with their consumers when [git.affected] consumers is on (--tests-only leaves them out), or ALL; unmapped files are named on stderr. It reads git objects at --head (each submodule at its pin), never the working tree. It needs only [git.affected], not an enabled workflow. Exit 0 with an answer, ALL included when the base does not resolve, equals the head or a manifest does not parse; 2 for a missing --base or an invalid table. --json prints the envelope pmcp.git.affected.v1, whose data has all, reason, base, head, changed, members, unmapped and selected (the printed list, or "ALL").

heavy

pmcp heavy -- npm test
pmcp heavy --lane bulk --weight 3 -- npm run build:all
pmcp heavy --profile gate --weight 2 -- npm run typecheck
pmcp heavy --profile hook -- npm run lint:staged
pmcp heavy --now --reason "prod is down" -- npm run deploy
pmcp heavy status [--json]
pmcp heavy stats [--top <n>] [--json]
ticket=$(pmcp heavy submit --lane bulk -- npm run build:all)
pmcp heavy result "$ticket"
pmcp heavy wait "$ticket" --timeout 1800
pmcp heavy cancel "$ticket" [--force]
pmcp heavy queue [--json]
pmcp heavy promote <id> --now --reason "release blocker"
pmcp heavy priority <id> gate --reason "blocks a land"
pmcp heavy priority <id> +2 --reason "the session waits on it"

Run a heavy command within the host-wide budget of [host.lease], across every session and worktree on the host. A job starts once its lane has a free slot, its weight fits what the running jobs leave of the budget, and the host is under max_load and max_io (or, past load_grace and with nothing leased running, under hard_factor times them). Waiting jobs start by lane (gate, hook, interactive, bulk), oldest first within a lane, with a line on standard error every heartbeat; --lane and --weight override the profile and [host.lease] commands. The command runs with the lease marker set, so a nested pmcp heavy runs at once. Everything after -- is the command, options included. status prints the lock, the host readings, when the host was last settled, the holder record, each waiter with its lane, weight, position and a rough wait estimate from the log's run times, the lanes' use and the running weight against the budget, each running job against hold_warn and hold_max, the IO average the check reads, how many jobs started on load_grace in the last day, and the busiest processes outside the lease. With the lease disabled (enabled = false), the command runs at once. With PMCP_HEAVY_DISABLE=<reason> set to an allowed reason (nested inside a leased job, operator for the operator, or one listed in [host.lease] skip_reasons or skip_always), an ordinary command runs at once and its usage record keeps the reason; any other reason runs nothing and exits 2 with the allowed list, but a bulk job (--lane bulk, or a commands entry with lane = "bulk") still queues in the bulk lane, with a line saying the skip was not honoured, unless [host.lease] skip_always lists the reason. --now --reason <text> (or PMCP_HEAVY_NOW=<reason>) is the operator's emergency bypass: it runs at once, logged and shown in status, and still counts its weight; from an agent session it exits 1 and names who to ask, as promote --now and cancel --force on another session's job do. Where the io controller reaches the user's scopes, each job runs in its own scope with its lane's io.weight. submit queues the command and returns a ticket at once, so the caller keeps working: a detached runner (its own session, so it outlives the caller) waits and runs it under the same rules, its output in the ticket's log and its exit code and usage record in the ticket's result. Every job keeps its stdout and stderr in its ticket, bounded by [host.lease] job_log_bytes (default 4 MiB, rotated once to log.1, so a job keeps at most twice that): a submitted job's runner writes them there, and a blocking run opens a ticket of its own and copies them there as they reach the terminal, so the command sees pipes instead of a terminal; a blocking run that fails ends with a line naming its id. job_log_bytes = 0, or a disabled lease, keeps nothing for blocking runs, which then write to the terminal directly. result <id> reads the state (queued with its position, running, done, or lost when the runner died), --json as data, and result <id> --log prints the kept output instead, the rotated part first; --tail <n> keeps its last n lines. wait <ticket> blocks until it is done, prints the log's tail and exits with the job's code (75 at --timeout); cancel <ticket> stops a queued job and, with --force, a running one. Tickets live under <dir>/tickets/ and finished ones are removed after a week. Every waiting or running job has an id (a ticket's, or one made for a blocking run), shown by status and queue: queue lists the waiters with id, lane, position, waited and estimated time, weight, pid, session and label; promote <id> --now --reason starts a waiter at once as a bypass; priority <id> <lane|+N|-N> --reason moves it to another lane's end or N places within its lane; cancel <id> takes a waiter out of the queue (its run exits 130) and, with --force, stops a running job. The waiting process reads the change on its next poll; each change is made under the admission lock and logged as a control line with the uid, the session and the reason, and a waiter whose process died is removed instead of changed. stats lists each command signature's recorded runs with the median and 90th percentile of wall time, CPU time, peak RSS and IO and how many skipped the lease, after a line with the share of all runs that skipped it and lines counting the skip reasons and the refused ones, the most-run first; --top <n> keeps the first n, --json as data. Exit: the command's own code; 75 when nothing ran within max_wait, with the reason (the queue, the session's cap, a shell wrapper's hold, a host past hard_factor); 2 for a missing --, an unknown profile or lane, a bad weight, --now without a reason, or a skip reason that is not allowed; 1 for an operator verb outside the operator's terminal.

host

pmcp host io measure [--dir <path>] [--seconds <n>] [--json]
pmcp host io plan [--unit <name>] [--json]
pmcp host io doctor [--weights [--seconds <n>]] [--json]

Fit the kernel's io.cost model to the disk, so the lanes' io.weight ([host.lease.io]) divides it. Linux with cgroup v2 only; elsewhere these exit 3. The kernel's own estimate (ctrl=auto) can overstate a network volume several times, and while it does, weights of 25 and 100 get nearly the same IOPS. A measured model alone is not enough: with qos ctrl=auto the kernel may raise vrate far past the model, so the model always comes with qos ctrl=user rpct=0 rlat=0 wpct=0 wlat=0 min=50 max=100.

measure waits for the host lease in the bulk lane with the whole budget, like any heavy job (75 when it never gets it), then probes a 1 GiB file on the filesystem of --dir (default: the lease directory) with O_DIRECT, so the page cache is bypassed; it never touches the raw device. The probe runs in its own systemd-run --user scope under pmcp-io.slice, outside the lanes' scopes and their io.max, and its directory is removed however it ends. It writes the file in 1 MiB blocks, then runs 1 MiB sequential reads at depth 4 and 4 KiB sequential and random reads and writes at depth 16 for --seconds each (default 8), about a minute in all, and records the model with the whole disk's major:minor (a partition resolves to its disk), the time, the pmcp version and the io.cost lines live at the time in <dir>/io-model.json of [host.lease]. While the device's qos is ctrl=user, vrate is held to the current model and a probe would measure that cap, so measure refuses before it takes the lease, with exit 4: it prints the line that lifts the cap (echo '259:0 enable=1 ctrl=auto' > /sys/fs/cgroup/io.cost.qos as root, for that device), and plan prints the capped line to restore afterwards. There is no override.

plan reads the record and prints, per device, the io.cost.model line, the io.cost.qos line and a systemd unit (pmcp-io-cost.service) that writes both at boot; --unit <name> prints a drop-in for an existing oneshot unit instead. It only prints: install the unit as root. Exit 1 without a record.

doctor only reads: it compares the live io.cost.model with the record and checks that qos is enabled, ctrl=user and max at most 100. --weights also runs two 4 KiB random readers at io.weight 25 and 100 in sibling scopes for --seconds (default 20), under the host lease like measure; each scope first checks that every cgroup above it has io in cgroup.subtree_control, since without it the weights are never read, and the check is reported as not valid instead of as a ratio. A ratio under 2 is a warning. Exit 0 when every check passes, 4 with a warning (no record included), 3 without io.cost.

wait

pmcp wait --pid 4242
pmcp wait --until gone:/tmp/build.lock --until load-below:6 --timeout 900
pmcp wait --until no-process:"vitest run"

Sleep until every condition holds: --pid until that process has exited, --until exists:<path>, gone:<path>, load-below:<n> (1-minute load average) or no-process:<text> (no command line contains the text). It never matches itself or the shells that started it, which a loop around pgrep -f does, and it sleeps between checks (--interval, default 5 s) instead of spinning. Exit 0 once met, 75 after --timeout (default 3600 s), 2 for an unreadable condition.

owners

Name who looks after each path, from [[owners]]: one line per matching entry, <path> belongs to <owner>: <note>, or <path>: no owner. Paths are taken from the working directory and matched relative to the directory holding pmcp.toml. --json gives paths, each with path and owners (owner, note, mode). It only reads. Exit 0, or 2 without a path or a pmcp.toml, or with an invalid [[owners]].

The workspace starts read only; taking control and stopping a runtime require explicit actions. Opening requires an interactive terminal and the same host as the harness. Keys, mailbox observation and cleanup.

The written skills

Local discovery, configuration and terminal supervision need no PMCP account. Configuration and supervision can change local state; native runtimes retain their own provider login requirements. Package-specific skills are free to read, download and install without PMCP login. Each skill page links the original SKILL.md and a content-only archive that your package manager can install directly. The service commands below also support hosted catalogs with their own access policies.

All four take --project <dir>, --api <origin>, --json, and --catalog <file>, which reads a saved response so the command runs with no network at all.

available

pmcp available [--project <dir>] [--catalog <file>] [--json]

Which written skills match the dependencies this project already has. It reads your package.json to decide what matches and does not upload it. No account needed.

preview

pmcp preview <skill-package> [--json]

A skill's contents and one complete example. The sample is taken from the skill's own bytes rather than described, so it cannot drift from what you would receive. No account needed.

login · logout · whoami

pmcp login [--issuer <url>]
pmcp logout
pmcp whoami [--json]

login signs this machine in without a browser: it prints a code and a URL to open anywhere. The credential is kept outside the project, so it cannot be committed or copied into an image. whoami answers on stdout, so a script can read it. This optional service login is not needed to use the free package skills on pmcp.build.

skills.modoo.today is a separate skill catalog service built on pmcp, with its own accounts and access policies; pmcp login and --provider hosted reach it. pmcp itself needs no account there.

install · sync

pmcp install <skill-package>... | --all [--dry-run | --yes]
pmcp sync [--project <dir>] [--dry-run | --yes]

install adds skill packages as dev dependencies with your own package manager, and what gets installed is checked against the digest the catalogue published — not its name and version, which any registry can claim. sync updates the ones already declared and removes nothing else. pmcp uses the free bundled public catalog by default and verifies immutable archives and installed resources without login. Explicit --provider hosted or --api selects a separate service's credentialed distribution, such as skills.modoo.today (see login).

Both show the project and lockfile changes and stop: --yes (-y) approves them, --dry-run prints the plan and changes nothing.

With TERM=dumb, or a locale that is not UTF-8, the few typographic characters in messages (an em dash, a middle dot) print as ASCII. Long operations such as index report progress on standard error: one rewritten line on a terminal, a plain k/N line every tenth of the work otherwise.

Help and tables fit the terminal: COLUMNS when set, else the terminal width, kept between 40 and 120 columns; long descriptions wrap under their column, and a name too wide for its column puts its description on the next lines. Status records (status, sessions status, heavy status, queue and stats, git worktree list) fit the same width on a terminal: a long record wraps under a hanging indent, and a word wider than the line is cut with an ellipsis. Off a terminal, help wraps at 80 columns and a table or status listing prints one plain record per line (name description, no padding), so grep and cut see whole records.

A reader that closes the pipe early, as pmcp list | head -1 or pmcp heavy stats | head does, ends the command quietly with exit 0 instead of a write error.

Options are parsed against the command's own list, so an unknown flag is an error rather than a silently ignored typo. Giving a non-repeatable option twice, or leaving off a value it needs, is the same error.

An unknown command, subcommand or option exits 2 with one line naming it, the closest valid name when one is near (unknown command "stauts"; did you mean "status"?), and where to look next (Run pmcp status --help for its usage.), rather than the whole help. An unknown subcommand also lists every valid one. pmcp help <command> for a command that does not exist is the same error. Every command that needs a pmcp.toml and finds none says so the same way and suggests pmcp init.

Exit codes

Every command uses one table, so a script can branch on the code alone:

CodeMeansFor example
0it did what you askedskills listed, the whole catalog indexed, nothing to deliver
1it ran and failed, or found a problemno skills under those roots, a partial index, no SQLite to store vectors in, validate errors, a doctor FAIL, a declined or failed install, a refused delivery, a failed gate or fetch
2usage error: it could not run as askedan unknown command, subcommand or option, a missing value, no pmcp.toml or a missing [git] table, git sync in the wrong checkout
3an optional dependency is missingindex without @huggingface/transformers, host io off Linux or without io.cost
4a check ran and found differencesstatus projection drift, project --check drift or an exceeded budget, stale or undeclared outputs, a hooks test --fixtures or --smoke finding, a host io doctor warning, host io measure refused under a capped qos
75the host stayed busy, so nothing ran; retry laterheavy or host io measure past max_wait, a git deliver gate whose test stage never got the host lease, wait past --timeout

1 says the project is not what you expected; 2 says the command line or the setup is wrong, so retrying the same command will not help; 3 says the machine is missing something optional and the server still works without it; 4 says a check did its job and found something to fix, usually with pmcp project. A command that runs another command, such as heavy, exits with that command's code. Before 0.23.0, drift exited 2 like a usage error; see Upgrading.

Results on stdout, diagnostics on stderr. What you asked for goes to standard output: the JSON from --json, the version, requested help, and the human result of a read (the list, models, marketplace list and doctor tables, validate findings, the status summary, hooks and sessions listings, an install or sync plan). So pmcp list | grep react and pmcp list > skills.txt work, and -q never erases a result. Progress, summaries such as "144 skills", warnings, hints and errors go to standard error. Before 0.23.0, human tables and help went to standard error; see Upgrading.

Runtime

  • Node 22 or later, or Bun 1.3 or later.
  • Runtime dependencies: @modelcontextprotocol/server, zod, semver, smol-toml and yaml. See dependency licence notices.
  • Vector storage uses whichever SQLite the running binary already has. Neither is a dependency; without one, the server still runs and ranking falls back.
