Docs / Hooks

Hooks

Back to the overview

[hooks] in pmcp.toml compiles guards, checks and session bookkeeping into one hook bundle that every targeted runtime runs on its tool calls. The other tables are in the pmcp.toml reference.

pmcp project compiles [hooks], [sessions], [git] and [logging] into .agents/pmcp-hooks/policy.json, copies the hook beside it as hook.mjs (a small loader) and hook-body.mjs, and registers hook.mjs in .claude/settings.json and .codex/hooks.json for the events the declared features use. Gemini, Antigravity, Grok and OpenCode are opt-in: name them in [hooks] targets and pmcp registers the same hook in their files (see Runtime support). pmcp.lock pins the hash of policy.json; the hook refuses to act on a policy that does not match it, so every policy change is a reviewed projection. Codex shows changed entries under /hooks as needing review; untrusted hooks do not run. Each Codex, Claude and Grok entry carries a statusMessage such as pmcp session start or pmcp before tool: Codex lists hooks under that name, and Claude and Grok show it while the hook runs. Gemini entries keep their name (pmcp-<event>), which is part of the identity Gemini trusts.

The hook keeps two per-user caches under $XDG_CACHE_HOME/pmcp (default ~/.cache/pmcp), never in the project: Node's compile cache for the body (hook-compile/) and the last integrity verdict per policy.json (hook-verified.json). A verdict is reused only while neither policy.json nor pmcp.lock has been written since. Either cache can be missing or unwritable without changing a decision; PMCP_HOOK_COMPILE_CACHE=off turns the compile cache off.

Every feature is opt-in: a table that is missing turns its feature off, and a declared table, even an empty one, turns it on. The exceptions are documented where they apply: [git] features detect git (enabled = "auto"), [git.shared_checkout] is on in any git checkout once the bundle exists, and logging falls back to its defaults rather than to no logging. The bundle is projected only when [hooks] declares guards or checks, a [sessions.*] feature table is declared, [git.shared_checkout] or [git.worktrees.sync] is declared, or [git.mainline.deliver] keeps refuse_direct_push.

[hooks.guards.<group>.<name>]

Each built-in guard is one table. mode is the only key the option-less guards take; an unknown option is an error. Modes: deny and ask replace the guard's verdict with that mode, warn turns the reason into context the agent reads, off drops the guard, and graded keeps the guard's own split between ask and deny.

[hooks.guards.shell.heredoc]denydeny, ask, warn, offHeredocs and here-strings, whose body the shell expands silently.
[hooks.guards.shell.stdin_interpreter]askdeny, ask, warn, offAn interpreter reading its program from stdin (python3 -, cat x.py | python3).
[hooks.guards.shell.compose_teardown]denydeny, ask, warn, offdocker compose down, and stop, rm or kill with no service named: they hit every service.
[hooks.guards.shell.secret_exfiltration]gradeddeny, ask, warn, off, gradedReading a credential asks; sending one over the network, or changing a live one, denies.
[hooks.guards.shell.host_approval]denydeny, ask, warn, offhost approve, and commands or edits touching the host approvals directory. On by itself when [host] is declared.
[hooks.guards.git.push_without_verify]denydeny, ask, warn, offgit push --no-verify.

Options:

  • [hooks.guards.shell.secret_exfiltration]: extra_secret_paths (list of case-insensitive regular expressions, default []), and [[hooks.guards.shell.secret_exfiltration.value_commands]] entries for a CLI that prints or publishes secret values: binary (required), read (verbs that print a value, so reading asks) and publish (verbs that change a live value, so they deny). Built in are .env files, .dev.vars, private keys, .npmrc, .netrc, auth.json and service-account files; a file whose name merely contains "secret" or "credential" is not one, so list such files in extra_secret_paths. Only a file a command reads counts: a search pattern, a sed or awk script, a jq filter or -e code that mentions .env does not.
  • [hooks.guards.git.gate_bypass_env]: names (variable names, default []) and no_verify (boolean, default true).

A mention is not a match: commands are parsed into steps, so git commit -m "never git push --no-verify" and echo 'cat <<EOF' pass. A command the parser cannot read is judged by a conservative pattern instead.

[hooks.failure]

What a guard that fails to evaluate means for the call: it threw, or it ran past timeout_ms. A guard's own deny is a verdict and is never affected. Without the table a failed guard refuses the call (a bookkeeping guard such as the session registry lets it through), as it always has.

KeyTypeDefaultMeaning
timeout_msinteger2000Longest one try of a guard may take (100 to 60000). The projected runtime timeout covers every try.
retryinteger1Further tries before the failure counts (0 to 3).
passlist[]What still goes through after the last try, with a warning: read (read tools) and edit-own-worktree (edits whose every path is inside the session's linked worktree, never the shared main checkout). Everything else, every shell call included, is refused.
[hooks.failure]
timeout_ms = 2000
retry = 1
pass = ["read", "edit-own-worktree"]

Either way the call carries one line naming the guard and the cause, e.g. pmcp hooks: sessions.leases failed (timeout 2000 ms); refused.

The stop check runs the checkout's own pmcp (node_modules), else the CLI that last projected this checkout on this machine (recorded in the state directory as projector.json), and only at the version pmcp.lock records. A pmcp on PATH is never used. When none matches, the session hears projecting pmcp not available once instead of a drift report.

Codex limits that shape the projection:

  • Codex has no ask. An ask becomes ask_fallback (deny by default).
  • Codex sends no agent_type, so roles cannot apply there.
  • Codex rejects context on Stop, so Stop notices are delivered at the next prompt.
  • Codex clamps a SessionEnd hook to 3 s; pmcp projects at most 3 s for it.
  • Codex has no Notification event.
  • Codex's own command filter rejects a fully quoted executable before any hook runs; use the ordinary unquoted form.

Gemini CLI 0.63.0, Antigravity (agy) 1.4.2, Grok 1.0.62 and OpenCode 1.18.33 are opt-in [hooks] targets. The pmcp bundle ran live on each in the same thirteen scenarios as Claude Code and Codex, judged from each runtime's own transcript; the live block of each capability file names the runs. A context a runtime does not deliver at an event is held and delivered at the next event that does, and that was measured live too. On OpenCode, prompt context goes into the system prompt, which OpenCode does not store, so its delivery is shown by a probe rather than by the prompt scenario. agy runs prompt policies on every turn: its counter resets per turn.

Where each runtime's projection goes, and what it needs:

  • Gemini: .gemini/settings.json hooks, timeouts in milliseconds. Gemini ignores project settings in a folder the user has not trusted, and records each new hook in ~/.gemini/trusted_hooks.json; pmcp doctor reads both and reports them, and never writes them. Trusting the folder is the user's step in an interactive gemini session.
  • Antigravity: one named set pmcp in .agents/hooks.json, beside the shell adapter's pmcp-shell. agy denies a tool call whose hook names no decision, so pmcp always writes one. agy has no session or prompt event: the first model call of a conversation is the session start, the first of a later turn the prompt. Whether that counter resets for a later prompt in an interactive session is not measured. No trust step.
  • Grok: grok also runs .claude/settings.json hooks, so with claude in [hooks] targets pmcp writes only the Claude file and the hook recognises a grok call by its payload; with Grok alone it writes .grok/hooks/pmcp.json. Never both, or every check would run twice. Project hooks run only after the user runs /hooks-trust; pmcp doctor reads ~/.grok/trusted_folders.toml without writing it.
  • OpenCode: there are no shell hooks, so pmcp writes .opencode/plugins/pmcp.js, a small plugin pinned in pmcp.lock that passes each call to the hook. A refusal is thrown as an error; Stop (session.idle) only updates the registry. No trust step.

auth = "pmcp" MCP servers project through pmcp project exec-mcp for every runtime above.

Deprecated shell guards

Deprecated: [[hooks.shell]] and [[hooks.edit]] still work, and pmcp project warns. Declare [[hooks.guards.custom]] instead, with on = "before_shell" or on = "after_edit", and list its runtimes in [hooks] targets: every runtime now has a hook bundle adapter, and this separate shell adapter will be removed in a later major release.

Declare a project-owned guard explicitly to project it into Codex, Gemini or Antigravity's native hooks. Without a declaration, pmcp generates no hooks.

[[hooks.shell]]
name = "shell-command-policy"
command = ["node", ".agents/guards/shell-command-policy.mjs"]
targets = ["codex", "gemini", "antigravity"]
timeout_ms = 15000

The guard script must exist under .agents/guards/ and cannot resolve outside that directory. It receives one JSON object on stdin containing runtime, event=before_shell, command and cwd. It returns a JSON object with decision=allow or decision=deny and an optional reason. Malformed responses, nonzero exits and timeouts deny the shell call. The guard receives PATH and LANG rather than the native CLI's credential environment. Non-shell tools are outside this contract.

Run pmcp project to write lock-owned adapter and policy artifacts under .agents/pmcp-hooks/, plus the native entries in .codex/hooks.json, .gemini/settings.json and .agents/hooks.json. Peer entries are retained. Edited owned hook entries refuse projection for review. Removing a declaration removes its generated entries and artifacts while preserving peer settings. Writes retain private backups; pmcp project --check only reports drift.

Guard, policy and adapter fingerprints bind the generated command. Changing guard code requires reprojection and native Codex hook review. Generated files contain no trust bypass. Grok can load Claude project hooks, so this first scope does not generate a second Grok guard. Hooks do not force pmcp catalog use, inject reminders or replace the runtime's execution sandbox.

Deprecated edit guards

Codex edit guards run after apply_patch through native PostToolUse hooks:

[[hooks.edit]]
name = "edit-policy"
command = ["node", ".agents/guards/edit-policy.mjs"]
targets = ["codex"]
timeout_ms = 15000

The guard receives runtime=codex, event=after_edit, the patch in command and cwd. It returns the same allow/deny response as a shell guard. A denial becomes native blocking feedback with the reason; the completed file edit remains on disk for correction. Other tools do not invoke this guard. Edit targets currently support Codex only, and names must be unique across shell and edit declarations.

Run pmcp project after declaring or changing the guard, then review and trust the generated native definition in /hooks. Peer entries and shell guards are preserved. Fingerprints and failure handling follow the shell-guard contract. See the native hooks documentation.
